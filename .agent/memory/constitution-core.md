# AIPos Constitution Core

This file is the default execution entrypoint for repository-wide rules.
Read this file first.
Return to [constitution.md](./constitution.md) only when the core rules here are insufficient for the active task.

## Default Read Order
1. Read this file first.
2. Read the relevant file in `rules-core/`.
3. Read `docs/memory/index.yaml`.
4. Read only the matching `docs/modules/<module>.md` brief.
5. Open `docs/modules-details/...` only when the brief is insufficient.
6. Leave `docs/modules-archive/...` and historical plan files closed unless the task truly depends on deep history.

## Non-Negotiable Rules
- Priority Zero: AI / agent must never modify the Git staging index. Do not run `git add`, `git restore --staged`, `git reset`, `git rm --cached`, or any equivalent command that stages, unstages, or rewrites staged files. If the user manually staged a file, preserve that staged state exactly.
- Engine Priority Zero — Entity relationships: every relationship between two `@entity` types in handwritten `base-engine/model/*.graphql` must be modeled with typed object/list fields and `@relationship`; never declare or use a custom scalar `xxxId` / `xxxIds` field (or a differently named scalar alias) to associate, join, query, or enforce referential linkage to another entity/table. This applies equally to runtime, history, audit, ledger, governance, and explicit association entities. Generator-owned FK columns and generated relationship ID inputs are implementation output, not permission to add handwritten scalar relationship fields. Plans, reviews, and implementations must stop on violations, and schema contract tests must enforce this boundary.
- One-operation exception (2026-09-07): the user authorized explicit task-only staging, commits, normal merges and verified cleanup solely for reviewed MCP integration from `merge/generic-mcp-redirect-authorization-1-1-0-rc` into `feature/instruction-1.1.0-rc` across root/Engine/App/Web. No push or changes to user-staged entries. It expires when that integration completes; see the scoped amendment in [constitution.md](./constitution.md).
- Standing workflow exception (2026-09-11): `creating-gitlab-issues-and-merge-requests` local-worktree publication may, only after a no-mutation preview and a separate explicit user confirmation, create/switch one generated feature branch, stage the confirmed paths, create one commit, and perform one normal non-force upstream push in `base-app`, `base-engine`, and `base-web`. It never covers the root repository, unrelated staged entries, force-push, amend, rebase, reset, restore, clean, stash, deletion, tag changes, merge, or automatic rollback. See the exact boundary in [constitution.md](./constitution.md).
- Never skip `spec -> plan -> tasks -> implement`.
- Cross-end impact gate: before implementing any new or changed feature, assess Engine, Web, and App consumers (including App mobile/desktop/tablet when applicable). Record each end's required change, compatibility verification, or reason no change is needed in the spec/plan; recheck that assessment during review. Checking an end does not require identical UI or feature rollout there. See Constitution §II-A.
- Engine API / AI tools sync gate: every new or changed user-facing business capability backed by an Engine operation must deliver its permitted read/action AI tools in the same task, or prove an existing tool covers the changed behavior. Record operation/tool IDs in spec/plan/task/review. `NON_CALLABLE` cannot defer missing tool work; an intrinsic security/product exclusion needs an operation-level reason and the user's explicit scope decision before implementation. Sensitive suboperations may remain excluded while safe parts receive tools. Pure visual/client-local changes need only a concrete no-impact reason. Inventory/tool parity, protected behavior tests, and `make check_ai_contracts` are mandatory. See Constitution §II-B.
- AI tool impact PR gate: Engine, Web, and App source-change PRs must include a structured `AI_TOOL_IMPACT` declaration with separate `impacts` entries for mixed outcomes, unique operation IDs, and evidence or a concrete no-impact reason; existing single-outcome declarations remain valid. Each repository's CI checks presence and format; reviewers must reject `NON_CALLABLE` used to postpone a business tool and verify any exclusion has the user's recorded scope decision. Inventory availability accepts only `CALLABLE`/`NON_CALLABLE`; tool permissions must match independent reviewed coverage and applicable GraphQL workspace permission directives. See Constitution §II-B.
- Callable AI tool quality gate: every callable tool must have a stable unique `name`, a human-readable `title`, a distinct detailed `description`, and a strict typed input schema with meaningful descriptions for nested parameters. Validate inputs both before business invocation and before issuing a write approval plan; enumerate all callable tools in regression checks. Non-callable contract records do not require executable tool metadata. See Constitution §II-B and Engine rule ENG-AI-009.
- Monetary and payment integrity gate: persist and calculate CNY amounts as integer fen, convert decimal yuan only at external boundaries without binary floating-point arithmetic, and keep estimated fees distinct from platform-confirmed fees. Any future payment flow must derive payable amounts on the server, retain business ownership and actual collecting merchant separately, protect provider credentials, and confirm payment through verified server-side evidence with idempotent state changes. See Constitution §II-C.
- `docs/modules/<module>.md` is the canonical module memory entrypoint.
- `docs/plans/task.md` is the default active-window tracker, not a long-term knowledge base. Inside a linked worktree, use a worktree-local tracker at `git rev-parse --git-path codex/task.md` instead.
- Long-lived history belongs in `docs/modules-archive/<module>/` or `docs/plans/archive/`, not in default read paths.
- Repo rules become stronger when backed by contract checks; do not rely on long-text rereads alone.
- Boundary tests must preserve real runtime shapes and relevant persistence constraints; fake fixtures do not count as boundary coverage.
- Handwritten Engine, Web, and App code must stay cohesive: at most 250 effective lines per file, 50 per function, cyclomatic complexity 10, and control nesting 3. Keep helpers near their consumers and reuse them only when semantics match. See the full constitution and stack rules for measurement, legacy baselines, and exceptions.
- `base-engine/gen/` must never be edited, formatted, or deleted directly by an AI/agent. Generation from handwritten `model/` changes is allowed only when the user explicitly authorizes it for the current task; use the repository's `make generate` command and review the complete generated diff. Otherwise stop before a schema change requiring generated output.
- Web admin form controls (`<Input>`, `<textarea>`, etc.) must define clear and meaningful `placeholder` attributes (`WEB-UI-006`); touch-chains and new dialogs/forms must not leave inputs without placeholders.
- Web admin forms and field row layouts must use `flex flex-col gap-5` (`WEB-UI-007`); legacy `space-y-*` layout classes in forms/dialogs are strictly prohibited.
- Web admin forms must never expose manual "编号" / "编码" (code/number) fields (`WEB-UI-008`); internal identifiers must be generated automatically upon creation without burdening users.
- Every Web admin user-entry control and visible form-item surface must use a white surface with black text (`WEB-UI-009`), whether it appears in a full-page create/edit flow, configuration or policy page, dialog, drawer, inline action panel, list filter, or portal-rendered option panel. Canonical admin-scoped/shared components must own this invariant; page-local white/black patches are not a substitute for shared coverage. New custom or composite control types must expose the shared form-surface contract and add automated coverage.
- Every Web admin entity list, including nested lists and pages outside the `*ListPage.tsx` naming pattern, must review its fields and workflow for useful filters (`Constitution §XVII`, `WEB-UI-010`). Filters must execute server-side before pagination, compose with search, reset pagination, clear together, and offer complete relationship choices and working load-error recovery; prove these behaviors in tests.
- Web UI must prefer official shadcn/ui components (`WEB-UI-011`): check the official catalog first, use an installed component when available, and install a missing official component into `base-web/src/components/ui` through the project's shadcn CLI configuration before considering custom primitives.
